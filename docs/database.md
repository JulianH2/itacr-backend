# Database model

The database is Azure SQL (production) and SQL Server 2025 in Docker (local). The schema lives in the SQL scripts of `database/` and reaches every environment through `Itacr.Database.Migrator` ([database/README.md](../database/README.md)). The API reaches it only through stored procedures, called with Dapper from the repositories in `src/Itacr.Infrastructure/Persistence/<Module>/`. This file explains the decisions that are not obvious from the code.

## Conventions

- **Table names**: plural PascalCase (`Orders`, `OrderItems`) in `dbo`. Columns are PascalCase and match the entity properties in `Domain/`, so Dapper maps rows by name.
- **Keys**: `Guid` (`uniqueidentifier`), generated by the repositories with `SequentialGuid.Create()` (sequential values for SQL Server, the same algorithm EF Core used in sprint 1).
- **Timestamps**: every table has `CreatedAt` and `UpdatedAt` (`datetime2`, UTC). The code that writes a row passes them from `TimeProvider` (`@Now` in the procedures); procedures never read the server clock. An order taken offline keeps the `CreatedAt` of the device.
- **Enums** are stored as text (`nvarchar`): the repositories pass `ToString()` and Dapper parses the text back. Every string has a maximum length.
- **Money** is `decimal(10,2)`.
- **Deletes**: nothing cascades except `Order` to `OrderItem`, `OrderNote`, and `OrderStatusHistory`. Products, employees, customers, and tables can never be deleted while an order refers to them.

## Order lifecycle

An order moves **one step at a time**: `New` → `InPreparation` → `Ready` → `Delivered`. `Delivered` is final and nothing skips a step. The only way back is undoing the last kitchen step (below). The rules live in `Itacr.Domain/Orders/OrderStatusRules.cs`, and `Order.TryChangeStatus(...)` applies them: it returns `false` and changes nothing when the step is not allowed, so a use case turns that into a `409` `Conflict` error.

Every status change, including the creation of the order, adds a row to `OrderStatusHistory` (`FromStatus` is null on the first row). `Order.TryChangeStatus` also sets `LastStatusChangeAt`, `ReadyAt` (when it becomes `Ready`), and `DeliveredAt` (when it becomes `Delivered`). `ChangedById` is the employee who made the change, or null when the system did.

`Order.Create(...)` builds a new order in `New` with its first history row (a `DineIn` order needs a table and a `TakeAway` order has none, otherwise it throws `ArgumentException`; the use case validator gives the user the Spanish message), and `Order.AddItem(...)` copies the unit price, computes the `Subtotal`, and recalculates `Total`. The domain never sets `OrderId` on items or history rows: the repository generates the keys (`SequentialGuid.Create()`), links each child to its order when it inserts, and the database assigns `OrderNumber`.

The table was added in `database/migrations/V002__add_order_status_history.sql` (ITACR-40).

## Kitchen queue

`GET /api/v1/kitchen/queue` (roles Kitchen and Manager) feeds the kitchen board of HU_04. It runs `dbo.usp_Order_GetActive`, which returns the orders in `New`, `InPreparation`, and `Ready` as **one result set** ordered by `CreatedAt` (then `OrderNumber`), whatever the channel, so a waiter order and a customer pickup order share one queue. The items of each order come in the same row as JSON (`ItemsJson`), so an order and its items are always read together and an item can never show up without its order. Delivered orders are not part of the queue.

An order synced late after being taken offline keeps its original `CreatedAt`, so it sits where that time puts it. `CreatedAt` is stored in UTC and the API writes it with a `Z`; the response also carries `serverTime`, so the board measures elapsed time with the server clock instead of the clock of the device.

The board polls this endpoint every 5 seconds. Real-time updates (SignalR) come with HU_09.

## Kitchen status changes and undo

HU_05 (ITACR-11) lets the kitchen move an order with a tap and undo an accidental one:

| Endpoint | Roles | Procedure |
| --- | --- | --- |
| `POST /api/v1/orders/{id}/status` with `{ "status": "InPreparation" }` or `"Ready"` | Kitchen, Manager | `usp_Order_GetStatus`, then `usp_Order_ChangeStatus` |
| `POST /api/v1/orders/{id}/status/undo` | Kitchen, Manager | Same |
| `GET /api/v1/orders/{id}` (detail and timeline) | Waiter, Kitchen, Manager | `usp_Order_GetById` |
| `GET /api/v1/orders/recent` (last 10 of the waiter, 12 hours) | Waiter | `usp_Order_GetRecentByWaiter` |

- **One step, no races.** The API reads the current status, checks `OrderStatusRules.CanChange`, and `usp_Order_ChangeStatus` updates the order only `WHERE Status = @FromStatus`. When two boards tap the same order, the second one changes nothing and gets `409` ("El pedido ya cambió de estado"). Delivered is not a kitchen step (`400`); it belongs to HU_10.
- **Times.** Each change sets `LastStatusChangeAt` and adds a history row; becoming `Ready` sets `ReadyAt`.
- **Undo.** Allowed only for the last change, when it was a kitchen step (`New` → `InPreparation` or `InPreparation` → `Ready`), made by the same employee, at most `OrderStatusRules.UndoWindow` (15 seconds) ago; the board offers it for less, to allow for the network. The undo is one more history row going back (nothing is deleted), and undoing `Ready` clears `ReadyAt`. An undo cannot be undone.
- **Timeline.** The detail lists every history row oldest first; `undone` is true for the rows that went back.

## Why `ClientOrderId` is unique

The waiter app works offline. A device generates a `Guid` for each order before sending it, and sends it again until the server confirms. Network failures, retries, and Background Sync can deliver the same order several times, even at the same moment from two requests.

The unique index on `ClientOrderId` is what guarantees no duplicates: the API looks the order up by that value first and returns the existing one, and when two requests race, the database rejects the second insert (SQL Server error 2601 or 2627) and the API returns the order that won. A check in code alone would not be enough, because two requests can both pass it before either one saves. `dbo.usp_Order_Create` saves the order, its items, and its first history row in one transaction: it first checks `ClientOrderId` under a range lock (`UPDLOCK, HOLDLOCK`), so a second request with the same value waits and then finds the first one, and it still treats a 2601/2627 from the unique index as "already saved". It returns `Created = 0` in both cases, and the API answers `200` with the saved order (`201` when it was created). Prices are read from `dbo.Products` (`usp_Product_GetByIds`), never taken from the request. `OrderNumber` is a different thing: a sequential, human-readable number for the kitchen and the customer, assigned by the database.

## Why `UnitPrice` is copied into `OrderItem`

`Product.Price` can change tomorrow, but an order taken today must keep what the customer was told. `OrderItem.UnitPrice` copies the price at order time, and `Subtotal` and `Order.Total` are computed from the copy. Reports and past orders never change when the menu is repriced, and the manager's sales totals stay correct. For the same reason the item stores the chosen `Size`, `Drink`, `Extras`, and `Exclusions` as values, not as references to the catalog.

### Why the catalog is in a migration script

The catalog is the same everywhere, has no secrets, and the app cannot work without it. Being in a migration script, it is versioned, reviewed in the PR, and applied in the same order on every machine and in Azure. The ids and timestamps are fixed constants (the same ones production has had since sprint 1), so the script is deterministic and runs only once. Changing a price later is a new migration script, never an edit of a merged one.

### Why employees are seeded in C#

- Their PINs must be hashed with `PasswordHasher<Employee>` (PBKDF2 with a random salt), the same hasher the API verifies with. A SQL script cannot produce those hashes.
- Production credentials must never be in code or in a migration, and they differ per environment. The seeder reads them from configuration and the test employees only exist in Development.
- The seeder checks what exists before it inserts (employees by email, and "a manager exists" for production), so it can run any number of times.

The migrator runs the seed after the scripts, in the environment it runs in: `Development` with `dotnet run` locally, `Production` in the deploy workflow. That process needs the `Seed` settings only for the first deploy to a new environment.

### Initial manager in production

The seeder creates the manager only if no manager exists. The settings are:

| Setting | Meaning |
| ------- | ------- |
| `Seed__ManagerName` | Full name |
| `Seed__ManagerEmail` | Email used to sign in |
| `Seed__ManagerPin` | PIN of exactly 4 digits (stored hashed) |

If any setting is missing or the PIN is not 4 digits, the seeder skips the manager and logs a warning (never the PIN). The manager should change the PIN after the first login. The placeholder phone `0000000000` is set because `Phone` is required.
